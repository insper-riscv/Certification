# Certification release

🌐 [Português](../../pt-br/act4/release.md) · [English](release.md)

## 1. What is published

When a whole certification passes, the workflow publishes a GitHub release with the logs attached. The release is the record of the certification: the ACT4 tests and gems come from the image `ghcr.io/insper-riscv/ci-act4:latest`, all of the same ACT4 commit, and that commit is in the description. Nothing in the repository pins the version of the suite.

A run in which any pair (profile, memory model) fails publishes nothing.

## 2. When the release is published

| Trigger | Workflow | What is certified | Title of the release |
| :--- | :--- | :--- | :--- |
| Push to `main` | `certification` | The whole minimal matrix. If a pull request already certified the same tree, its result is reused. | The combination that was validated, for example `RV32 I/E M, Zmmul, Zicclsm, Zihintntl` |
| Manual | `certification` | The whole minimal matrix | Date and time in UTC, `YYYY-MM-DD HH:MM UTC, matrix` |
| Manual | `certification-profiles` | The exhaustive matrix, chosen at the dispatch, with the key `CERTIFICATION_RUN_SECRET` | Date and time in UTC, `matrix` |
| Manual | `certification-profile` | One profile and one memory model | Date and time in UTC, `profile <name>` |

The tag is unique, in the format `cert-YYYYMMDD-HHMMSS-<7 of the commit>`, because several certifications can have the same title.

## 3. What the description holds

| Item | Content |
| :--- | :--- |
| Profiles | Every profile tested in the matrix, or the single profile of a one-profile manual run |
| ELFs per module | How many ELFs passed in each module (I, E, M, Zmmul, Zicsr, Zicntr, Zihpm, Zicclsm, Zifencei, Zimop, Zicond, Zihintntl, Zihintpause) |
| Memory | For each profile, the model used: ROM and RAM inside or outside the chip and whether there are instruction and data caches |
| Versions | The ACT4 commit of the image, the Insper-RISC-V commit and the Certification commit |
| Run | The address of the run that produced the result, and of the reused run when there was reuse |

The automatic title lists only what was actually validated: the I or E base enters if at least one profile of it passed, and the modules enter in canonical order.

## 4. The attached logs

Each profile has a file `logs-<profile>.tar.gz` with the `latest.log` of the certification and the verdict of each ELF. Each attachment is under 2 GiB.

## 5. How the result of a pull request is reused

The pull request runs the minimal matrix and, when it passes, uploads the artifact `ci-pass-act4-<key>` with the results. The key comes from the action `ci-plan` of Infra and includes the digest of the `ci-act4` image, so a new image, with another ACT4 commit, never reuses the result of an old one. On a push to `main`, if the key is the same, the job `act4` is skipped and the job `release` assembles the release from that result.

## 6. Coverage

The job `plan` fails when the union of the ELFs of the planned profiles differs from the set of ELFs that ACT4 generates for the extensions of the core in the I and E bases, or when `matrix.md` does not hold the numbers of the matrix. The numbers of `matrix.md` are generated by `tools/riscv_build/act_docs.py`.
